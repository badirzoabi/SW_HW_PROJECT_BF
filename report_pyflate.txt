1. OVERVIEW
--------------------------------------------------------------------------------
pyflate is a pure-Python, stand-alone DEFLATE (gzip) and bzip2
decoder/decompressor (originally by Paul Sladen). The pyperformance benchmark
decompresses a fixed embedded bzip2 file (`interpreter.tar.bz2`, ~66 KB
compressed / ~390 KB decompressed) and checks the output's MD5 hash.

No third-party libraries are used - it is a from-scratch decompressor,
implementing:
  - a bit-level stream reader (`BitfieldBase`/`RBitfield` for bzip2's
    MSB-first bit order, `Bitfield` for gzip's LSB-first order),
  - canonical Huffman decoding (`HuffmanTable`/`OrderedHuffmanTable`), used by
    both the bzip2 and DEFLATE code paths,
  - bzip2-specific stages: Move-To-Front (MTF) decoding, the inverse
    Burrows-Wheeler Transform (BWT), and a run-length decode step,
  - DEFLATE-specific stages: LZ77 back-reference copying (gzip path; not
    exercised by this benchmark's bzip2 input).
Data structures are all built-in: Python lists (bit buffers, MTF state,
Huffman code tables as sorted lists of small objects) and bytes/bytearray for
the decompressed output.

2. INITIAL ANALYSIS
--------------------------------------------------------------------------------
Environment: same QEMU guest as nbody, profiled with
`perf record -F 999 -g -- python3-dbg -m pyperformance run --bench pyflate`
per the course guide, flame graph via FlameGraph (results/pyflate_baseline.svg).
5,710,164 samples were captured (401 MB perf.data) - by far the heaviest
profile of the two benchmarks, reflecting how much per-symbol Python work a
bzip2 decode does. A condensed dump is in
results/perf_report_pyflate_raw.txt (full report_pyflate.txt from the course
`perf report --stdio` command is 26 MB and is not included in the repo; the
raw perf.data / json / logs backing this report are on request).

pyperformance official baseline (--bench pyflate): 17.1 sec +- 0.7 sec.
Standalone pyperf baseline against the identical VM-installed source
(pyflate/orig/run_benchmark.py): 17.6 sec +- 1.3 sec.

perf report top hotspots: after the expected `_PyEval_EvalFrameDefault`
(bytecode dispatch, ~21% self), the next-largest chunks of the profile are
CPython's *debug allocator* bookkeeping - `_PyMem_DebugCheckAddress`,
`_PyMem_DebugRawFree`, `__memset_sse2_unaligned_erms` (poisoning freed/new
memory), plus `list_dealloc`/`list_resize` and, in the "unknown" buckets that
resolve after crossing freed/poisoned memory, integer-object churn
(`PyLong_FromLong`, `long_richcompare`, `binary_op1`). In other words: the
dominant cost after raw interpretation is Python OBJECT ALLOCATION/DEALLOCATION
churn, not any single arithmetic step. This is consistent with two specific
lines in the hot decode path:
  - `move_to_front(l, c)`: `l[:] = l[c:c+1] + l[0:c] + l[c+1:]` builds THREE
    new list slices and concatenates them into a FOURTH new list, on every
    call - and it is called once per decoded MTF symbol (i.e. very hot: this
    is inside `decode_huffman_block`'s main loop, executed roughly once per
    output byte).
  - `RBitfield._more()` reads the input ONE BYTE AT A TIME through a Python
    file object (`self.f.read(1)` + `ord(c)`), called millions of times over
    the life of a decode.
  - `HuffmanTable.find_next_symbol()` does a LINEAR SCAN over the whole sorted
    code table for every decoded symbol (up to ~258 entries), each scan step
    doing a `snoopbits()` call and an attribute compare.

3. OPTIMIZATIONS
--------------------------------------------------------------------------------
All three hotspots above were fixed, keeping the algorithm and every other
line of the decoder (BWT, RLE, MTF selection logic, block structure) byte-for-
byte unchanged - see pyflate/OPTIMIZATION_PLAN.txt for the original recipe and
pyflate/opt/run_benchmark.py for the applied diff against pyflate/orig/
(the exact source copied off the course VM's installed pyperformance package).

  OPT-1 (bit reader). RBitfield now operates on a pre-loaded, in-memory
  `bytes` buffer (read once, outside the timed decode) instead of a live file
  object; `_more()` indexes directly into the buffer and increments an
  integer position, removing the per-byte Python file-method-call overhead.
  Past the end of the buffer it virtually pads with zero bits instead of
  raising, which only matters for the harmless one-time over-peek used by
  OPT-3's table lookup - real decode always terminates via in-stream markers
  before that data would affect the output.

  OPT-2 (move_to_front). Replaced the triple-slice-and-concatenate with an
  in-place `del l[c]; l.insert(0, v)` on the same list object - same result,
  zero new list objects allocated. This is the change most directly aimed at
  the profile's dominant cost (allocator churn).

  OPT-3 (table-driven Huffman decode). Added a precomputed direct-lookup
  table per Huffman table: index by the next `max_bits` bits of the stream,
  value is `(symbol, actual_code_length)`. Every code of length L fills the
  `2**(max_bits-L)` table slots whose top L bits equal its canonical code
  value (standard table-driven Huffman decode), turning each symbol decode
  into one array index instead of an O(table size) linear scan. Capped to
  `max_bits <= 15` to bound the one-time table-build cost (bzip2's format
  allows up to 20-bit codes in principle, but real tables are far shorter);
  the original linear scan remains as a correctness-preserving fallback for
  the (unexercised, by this data) gzip "reversed" match mode and for the rare
  table exceeding the cap.

Correctness was verified two ways:
  (a) a standalone `pyflate/correctness_check.py` that runs orig and opt
      directly (no pyperf harness) on the real benchmark input and asserts
      byte-for-byte identical output plus matching MD5:
        orig: 399360 bytes, md5=afa004a630fe072901b1d9628b960974
        opt : 399360 bytes, md5=afa004a630fe072901b1d9628b960974
        CORRECTNESS: PASS (byte-identical output)
  (b) the benchmark's own built-in MD5 assertion (`bench_pyflake`), which
      passes for both orig and opt when run through `pyperf compare_to` below.

4. PERFORMANCE COMPARISON
--------------------------------------------------------------------------------
Fast single-decode check (pyflate/correctness_check.py, bypasses pyperf's
warmup/calibration overhead - useful as a quick sanity number):
    orig: 16.984 s   opt: 11.522 s   -> 1.47x faster

Official measurement via `pyperf compare_to` (results/pyflate_compare.txt),
same protocol as nbody:

    Mean +- std dev: [pyflate_orig] 17.6 sec +- 1.3 sec
                   -> [pyflate_opt]  11.7 sec +- 0.9 sec
                   : 1.50x faster  (~33% reduction in wall time)

This clears the assignment's >=7% bar by a wide margin, and - combined with
nbody's 1.58x - gives two benchmarks each independently past 7%, satisfying
the project's "two or more benchmarks at >=7%" criterion.

5. HARDWARE ACCELERATION PROPOSAL
--------------------------------------------------------------------------------
Target: the bit-reader + canonical Huffman decode stage (the two hottest
software operations identified above), implemented in SystemVerilog under
hardware/pyflate/ (bit_buffer.sv, huffman_decoder.sv, huffman_accel.sv,
tb_huffman.sv, full writeup in hardware/pyflate/HARDWARE.md). Simulated and
passing: `TB PASS: decoded {0,2,1} == {0,2,1}` (Icarus Verilog, iverilog
-g2012). Unlike the nbody PE, this design is fully INTEGER - no floating
point - and fully synthesizable as described.

  - Block diagram: AXI4-Lite MMIO control (CTRL/NSYM/STATUS/COUNT plus
    table-load registers) + a byte-stream DMA input feeding an 8-bit
    MSB-first `bit_buffer` (refills a byte when empty, natural back-pressure
    when starved), which feeds one bit per cycle into a `huffman_decoder` FSM
    that emits a stream of decoded symbols.
  - Inputs/outputs: 8-bit compressed byte-stream input with valid/ready
    handshake (DMA in); `SYMW`=9-bit decoded symbol output with valid/ready
    handshake (DMA out), symbols 0..511 (`MAXSYM=512`); parameters
    `MAXLEN=15` max code length; target 300-600 MHz (short integer critical
    path, no FP).
  - Architecture: the standard zlib-style canonical-Huffman decode FSM -
    registers `code, first, index, len`; each cycle it folds in one new bit,
    compares `code-first` against a per-length count `cnt[len]`, and either
    emits `symbol[index + (code-first)]` or advances to the next code length.
    `cnt[1..MAXLEN]` and `symbol[]` are small RAMs loaded once per Huffman
    table over MMIO (built host-side from the code lengths pyflate already
    parses out of the bzip2 stream header).
  - HW/SW interface: a CPython C-extension replaces pyflate's per-symbol
    `find_next_symbol()`/bit-reading loop for each Huffman block: it programs
    `cnt[]`/`symbol[]`, sets `NSYM`, pulses `start`, DMAs compressed bytes in
    and decoded symbols out. The remaining bzip2 stages (MTF, RLE, inverse
    BWT) stay in software initially (or become follow-on accelerator stages);
    the public `pyflate` decompress API is unchanged, with a software fallback
    if the device is absent - matching the "don't break user code" pattern.
  - Justification: this is precisely the millions-of-tiny-Python-operations
    hotspot the profile identified (bit-at-a-time reads and per-symbol linear
    Huffman scans, both now also optimized in software per section 3) -
    exactly the kind of fine-grained, high-repetition-count, branch-light
    operation that is cheap in a small FSM and expensive through a Python
    interpreter. Estimated throughput: ~1 bit/cycle through the FSM, i.e.
    roughly 1/(average code length) symbols/cycle; at 500 MHz with ~8-bit
    average codes that is on the order of 60M symbols/s.
  - Trade-offs: area is very small - a handful of registers, an adder, a
    comparator, and two small RAMs (`cnt`: ~15x16b, `symbol`: ~512x9b);
    frequency is high since the datapath is integer add/compare only with a
    short critical path; power is dominated by the small RAMs and the bit
    shifter, with energy-per-decoded-symbol orders of magnitude below a CPU
    executing interpreter bytecodes for the same symbol. A faster but larger
    variant trades area for throughput: a lookup-table front end that peeks
    `MAXLEN` bits directly (this project's own OPT-3 software optimization is
    the software analogue of exactly this idea) decodes 1 symbol/cycle but
    costs `2**MAXLEN x (SYMW+4)` bits of table RAM; a two-level table
    (root + sub-tables for long codes, as zlib does) is the usual production
    compromise. The serial FSM described here is the smallest, always-correct
    baseline. Assumption: canonical length-limited Huffman tables with
    MAXLEN<=15 (true for bzip2 by format), and that DMA can keep the FSM fed
    at line rate.

ESTIMATED OVERALL SPEEDUP (Amdahl's Law)
--------------------------------------------------------------------------------
The accelerator is a design proposal (per the spec, not synthesized or
physically run), so its effect on *overall* program time is estimated, not
measured - via Amdahl's Law: overall_speedup = 1 / ((1-f) + f/s), where f is
the fraction of total runtime the accelerator replaces and s is the
per-component speedup the hardware gives that fraction.

  f (accelerated fraction). perf's raw report only resolves to C-level symbol
  names (`_PyEval_EvalFrameDefault`, allocator internals, etc.), which cannot
  be cleanly split into "time in Huffman decode" vs. "time in BWT/MTF/RLE".
  For an honest f, the **original** decoder (pyflate/orig/run_benchmark.py,
  unmodified) was re-run under Python's own deterministic profiler
  (`cProfile`) on a single real decode of the benchmark's actual input file,
  and self-time (`tottime`: time inside a function, excluding its own
  sub-calls, so bit-reading time inside a Huffman-lookup call is not double
  counted) was bucketed into exactly the two classes of function the
  accelerator replaces:
      bit-reading   (RBitfield: readbits/needbits/_more/snoopbits/_read) :  27.70%
      Huffman match (HuffmanTable.find_next_symbol)                     :  15.85%
      -----------------------------------------------------------------------
      f = combined                                                      =  43.55%
  (decode_huffman_block's own loop-control/MTF-dispatch code, move_to_front,
  bwt_reverse/bwt_transform, and the RLE step are NOT in this bucket - they
  stay in software either way, exactly matching the accelerator's stated
  scope in the HW/SW interface above.)

  Caveat: cProfile is a deterministic profiler and adds per-call
  instrumentation overhead (this run took 35.96s vs. pyperf's uninstrumented
  ~17.6s mean for the same decode); since that overhead scales with call
  count and the bucketed functions are the highest-call-count ones (up to
  655,017 calls), f=43.55% may be a mild overestimate of the true
  uninstrumented fraction. Full raw output: results/pyflate_cprofile_hw_fraction.txt.

  s (per-component hardware speedup). The accelerated component decoded
  148,271 Huffman symbols. Scaling cProfile's bucketed time to the real
  (non-instrumented) `pyperf`-measured original run (17.6 s mean) gives
  component time ~= f * 17.6 s ~= 7.67 s -> a software rate of
  ~= 148,271 / 7.67 s ~= 19,300 symbols/s. Against the hardware's own
  ~60,000,000 symbols/s estimate (section above), s ~= 60,000,000 / 19,300
  ~= **~3,100x** at the component level.

  Overall estimate: 1 / ((1 - 0.4355) + 0.4355/3100) = 1 / (0.5645 + 0.00014)
  ~= **1.77x** predicted overall speedup from hardware acceleration alone
  (i.e. applied to the *original*, not the already-software-optimized,
  decoder - the same baseline the profile fraction was measured against).

  Sensitivity check: because s is so large, the result barely depends on
  getting s exactly right - even an infinitely fast accelerator (s -> inf)
  only reaches 1/(1-f) = 1/0.5645 ~= 1.77x, and a deliberately pessimistic
  s=50 (e.g. dominated by DMA/handoff overhead) still gives ~1.74x. The
  estimate is therefore robust to the s assumption; it is capped by f, not by
  s - the classic Amdahl's-Law lesson, and a concrete argument that a *second*
  accelerator stage (e.g. offloading MTF or the inverse BWT too) would be the
  next place to look for further overall speedup, since ~56% of total time
  lies outside what this one accelerator touches.

6. CONCLUSION
--------------------------------------------------------------------------------
Profiling under `perf`+flame graph on the debug Python build showed that
pyflate's cost is dominated less by any single "expensive" line and more by
sheer repetition: millions of one-byte file reads, millions of small-list
reallocations in the MTF step, and per-symbol linear Huffman-table scans, all
visible in the profile as CPython allocator/object-churn overhead rather than
useful arithmetic. Fixing exactly those three hotspots - buffered bit reading,
allocation-free move-to-front, and table-driven Huffman decode - preserved the
decoder's output byte-for-byte (verified independently of the benchmark's own
MD5 check) while delivering a measured 1.50x / ~33% speedup via the official
`pyperf compare_to` protocol, well past the assignment's 7% bar. The proposed
Huffman-decode accelerator is the natural hardware continuation: it takes the
exact same two operations optimized in software (bit reading and Huffman
symbol lookup) and moves them into a small, integer-only pipeline where "one
symbol per few cycles" replaces "one symbol per dozens of Python bytecodes".
Its own component-level speedup is enormous (~3,100x, by estimate), but
Amdahl's Law caps the *overall* program benefit at ~1.77x, because the
accelerated stage is only 43.55% of total runtime (measured via `cProfile` on
the original decoder) - a result that is itself a useful finding: it argues
for offloading a second stage (MTF or inverse BWT) as the next step, rather
than over-investing in an already-near-optimal Huffman engine.
