Per the project's AI-tools clause, this file documents how we used an AI
assistant (ChatGPT-style) during the project. We did the analysis, the
decisions, the measurements, and the design ourselves; we used the assistant
as a sounding board and for specific implementation/explanation help. Below is
a condensed, representative transcript of the way we worked, phase by phase.

--------------------------------------------------------------------------------
PHASE 0 — Choosing benchmarks
--------------------------------------------------------------------------------
US: We have to pick 2 of the approved pyperformance benchmarks. We're leaning
    toward one compute-bound and one control-bound so the two optimization
    stories are different. Does nbody + pyflate make sense?
AI: That's a good split — nbody is FP/interpreter-bound, pyflate is
    allocation/bit-manipulation-bound. Both are pure Python so all overhead is
    interpreter-visible.
US: Good, we'll go with nbody + pyflate. We'll start by profiling both.

--------------------------------------------------------------------------------
PHASE 1 — Profiling & reading the flame graphs
--------------------------------------------------------------------------------
US: We ran `perf record -F 999 -g` on python3-dbg and generated flame graphs.
    For nbody the widest boxes are _PyEval_EvalFrameDefault (~35%) and a bunch
    of float boxing / list-subscript functions. The actual float_mul/pow are
    tiny. So our read is: the bottleneck is interpreter + list access, not the
    math. Agree?
AI: Agree — that matches the profile. The FP ops being ~2% each means the FPU
    is idle most of the time.
US: Right. For pyflate we used cProfile too (perf only shows C-level names),
    and move_to_front + the bit reader + find_next_symbol dominate.

--------------------------------------------------------------------------------
PHASE 2 — nbody optimization (and an idea we rejected)
--------------------------------------------------------------------------------
US: The inner loop uses (dx^2+dy^2+dz^2)**-1.5. Our first instinct was to swap
    it for dt/(d2*sqrt(d2)) using a hardware sqrt. We implemented it and
    measured ~1%. Basically nothing.
AI: Consistent with the profile — pow is only ~2.5%, so by Amdahl the ceiling
    on that change is tiny.
US: Exactly, so we dropped it. Since there are only 5 bodies, we rewrote the
    force loop to keep all state in local scalars (read once, write back once)
    instead of list subscripts. That measured 1.58× / ~37%, output identical.
AI: Nice — that targets the real cost (list indexing + interpreter dispatch).
    Want me to help generate the unrolled straight-line version so the physics
    stays in one place?
US: Yes, generate it from the body list at import — we'll review it and check
    the energy checksum matches (-0.169089263). [It did.]
US (later): We also checked whether a 2nd nbody optimization was worth adding.
    We benchmarked factored-force and reciprocal-mul variants — both came out
    SLOWER (-8% and -6%). So nbody stays as one optimization; we won't pad it.

--------------------------------------------------------------------------------
PHASE 3 — pyflate optimizations
--------------------------------------------------------------------------------
US: From the profile we're targeting three things: move_to_front rebuilds 4
    lists per symbol, the bit reader does f.read(1)+ord per byte, and
    find_next_symbol does a linear table scan per symbol.
AI: Those are the classic pyflate hotspots. For MTF, an in-place del+insert
    removes the allocations; for the reader, buffer the input and index it;
    for Huffman, a precomputed lookup table gives O(1) per symbol.
US: That's what we did (OPT-1/2/3). We kept every other line unchanged and
    verified byte-for-byte with MD5. Measured 1.50× / ~33%.

--------------------------------------------------------------------------------
PHASE 4 — Hardware acceleration: scope decision
--------------------------------------------------------------------------------
US: We re-read the spec (p.4 item 7): "one or two key components of THE
    benchmark." We read that as: at least ONE benchmark needs hardware, not
    both. So we'll feature hardware on pyflate and keep nbody software-only.
    Do you agree that's a valid reading?
AI: Yes — "the benchmark" (singular) + "if applicable" in the report section
    supports one benchmark. nbody already has a strong software story.
US: Good. We'll design the pyflate Huffman decode engine first, since bit-read
    + Huffman is the biggest hardware-friendly chunk (43.55% from cProfile).

--------------------------------------------------------------------------------
PHASE 5 — RTL design & the second component
--------------------------------------------------------------------------------
US: We wrote the Huffman engine in SystemVerilog: bit_buffer + a canonical
    code/first/index FSM + table RAMs, MMIO + streaming. Our testbench passes
    (decoded {0,2,1}). Can you sanity-check the canonical-decode step?
AI: The code|=bit / compare (code-first) vs cnt[len] / advance logic is the
    standard zlib inflate decode — looks right.
US: We then decided the spec's "one or two components" lets us add a second
    component. We picked MTF (next-biggest chunk ~10.3%, and a clean register-
    file shift) over RLE/BWT. We wrote mtf_unit.sv + testbench (MTF decoded
    {30,30,60} passes).
AI: Good call — MTF pairs naturally after Huffman and is a clean 1-symbol/clock
    shift. RLE would've been too small to move the Amdahl number.

--------------------------------------------------------------------------------
PHASE 6 — Estimating the hardware speedup (Amdahl)
--------------------------------------------------------------------------------
US: Since we don't synthesize/run the accelerator, we estimate its effect with
    Amdahl. We measured f with cProfile: bit-read 27.70% + Huffman 15.85% =
    43.55% for component A → ~1.77× alone; adding MTF (~10.3%) → f≈53.85% →
    ~2.16×. We added a sensitivity check (capped by f, not s).
AI: That's the right framing, and stating it's an estimate (not synthesized)
    is the honest thing per the spec.

--------------------------------------------------------------------------------
PHASE 7 — Write-up, scripts, presentation
--------------------------------------------------------------------------------
US: We wrote report_nbody.txt / report_pyflate.txt, the script_*.sh runners,
    README, and the slides ourselves. We used you to review wording, catch
    inconsistencies (e.g. a stale "1.77×" after we added MTF), and to tidy
    over-verbose code comments.
AI: Happy to review — flagged the stale numbers and a mislabeled profiling
    table; the technical content and results are your own measurements.

--------------------------------------------------------------------------------
SUMMARY OF HOW AI WAS USED
--------------------------------------------------------------------------------
- Decisions (benchmark choice, what to optimize, one-vs-two hardware, which
  second component, keeping nbody software-only): OURS.
- Measurements (perf, flame graphs, cProfile, pyperf compare_to, MD5, RTL
  simulation): run and interpreted by US.
- AI assistance: explaining CPython/perf internals, confirming our profile

All AI output was checked and validated by us against real measurements before
being used, as required by the course policy.
